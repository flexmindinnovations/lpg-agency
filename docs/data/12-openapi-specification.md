# 12 — OpenAPI Specification

## Purpose
Defines the structure of the platform's OpenAPI 3.1 specification as auto-generated by FastAPI from Pydantic v2 models and route metadata: module organization, reusable schemas, security schemes, and versioning strategy.

## Scope
Structural design only — FastAPI generates the actual spec from code; this document defines the conventions that code must follow so the generated spec is consistently organized and genuinely useful to integrators.

## Design Decisions
- **Code-first, not spec-first**: Pydantic v2 models and route decorators are the source of truth; FastAPI's built-in OpenAPI generation produces `/openapi.json` automatically. This document constrains *how* routes/models are written so the generated output is well-organized, not a separately hand-maintained YAML file that could drift from the implementation.

## 1. Top-Level Structure (Generated Shape)

```yaml
openapi: 3.1.0
info:
  title: LPG Agency Management Platform API
  version: "1.0"
servers:
  - url: https://api.lpgplatform.com/api/v1
  - url: https://staging-api.lpgplatform.com/api/v1
tags:
  - name: Auth
  - name: Customers
  - name: Orders
  - name: Routes
  - name: Inventory
  - name: Ledger
  - name: Invoices
  - name: Payments
  - name: Complaints
  - name: Reports
  - name: Tenants
paths: {}
components:
  schemas: {}
  responses: {}
  parameters: {}
  securitySchemes:
    bearerAuth: {type: http, scheme: bearer, bearerFormat: JWT}
security:
  - bearerAuth: []
```

## 2. Schema Organization (By Pydantic Module)

Pydantic models are organized in a package structure that maps 1:1 to the generated `components/schemas` grouping:

```
app/schemas/
  auth/          OtpRequest, OtpVerify, TokenPair, LoginRequest
  customers/     Customer, CustomerCreateRequest, CustomerAddress, KycDocument
  orders/        Order, OrderCreateRequest, OrderLine, DeliverOrderRequest, CancelOrderRequest
  delivery/      Route, RouteStop, ProofOfDelivery, VehicleLoadRequest, ReconciliationRequest
  inventory/     InventoryBalance, InventoryAdjustmentRequest, GoodsReceiptNoteRequest
  ledger/        LedgerBalance, LedgerTransaction
  accounting/    Invoice, Payment, CreditNote
  complaints/    Complaint, ComplaintCreateRequest, ComplaintResolveRequest
  reports/       DailySalesReport, ReportExportJob
  common/        PageInfo, ProblemDetails, ProblemDetailsValidation, Money
```

- **Request/Response separation**: every mutating endpoint has a distinct `*Request` Pydantic model, never reusing the response model for input (server-computed fields — `id`, `status`, audit fields — are never client-suppliable; enforced by simply not including them in the `*Request` model's field set).
- **Enums as shared Pydantic/Python `Enum` types**: `OrderStatus`, `CustomerType`, `CylinderStatus`, `ComplaintPriority`, `LedgerTransactionType`, etc. are each defined once (Python `StrEnum` for clean JSON serialization), imported everywhere they're referenced — FastAPI automatically surfaces them as named, reusable `components/schemas` enums in the generated spec, not inlined per usage.

## 3. Path Organization (Module-Tagged via FastAPI Routers)

Each bounded context gets its own `APIRouter` with a `tags=[...]` and `prefix=...`, included into the main app — this is what produces the module-tagged path grouping in Swagger UI:

```python
# (illustrative structure only, not implementation)
orders_router = APIRouter(prefix="/orders", tags=["Orders"])
# @orders_router.post("", ...) -> operation_id="create_order"
# @orders_router.post("/{order_id}/deliver", ...) -> operation_id="deliver_order"
```

`operation_id` follows `verb_noun` (FastAPI's `generate_unique_id_function` configured accordingly), directly driving generated client method names across the Angular Dashboard's typed client and both Flutter mobile apps' API client packages.

## 4. Reusable Common Responses

Modeled as shared Pydantic response models referenced via FastAPI's `responses=` parameter on every route:

```python
# (illustrative)
COMMON_RESPONSES = {
    400: {"model": ProblemDetailsValidation, "description": "Validation failure"},
    401: {"description": "Missing/invalid authentication"},
    403: {"description": "Insufficient permission"},
    404: {"description": "Not found or not in caller's tenant"},
    409: {"model": ProblemDetails, "description": "Business-rule conflict"},
    429: {"description": "Rate limited", "headers": {"Retry-After": {"schema": {"type": "integer"}}}},
}
```
Every route merges `COMMON_RESPONSES` with its own success-response definition — guaranteeing consistent error shapes across all ~10 bounded contexts' worth of endpoints without hand-repeating the schema per route.

## 5. Reusable Parameters
Shared Pydantic "query parameter" dependency classes (FastAPI `Depends()`) for `page`, `page_size`, `sort`, and the `Idempotency-Key` header — defined once, injected wherever needed, so their OpenAPI parameter definitions are generated consistently everywhere they're used.

## 6. Security Schemes
- `bearerAuth` (JWT) is the sole scheme — no API keys, no basic auth in the public API surface.
- Public endpoints (`/auth/otp/request`, `/auth/login`, `/auth/password-reset/*`) explicitly override the global security requirement to `[]` in FastAPI's route-level `dependencies`/`security` override.
- No `tenant_id` parameter appears anywhere in the spec — tenant scoping is entirely implicit via the JWT claim (`17-api-security.md`).

## 7. Versioning Strategy
- One FastAPI `app` mount point per major version (`/api/v1`, `/api/v2` when it exists — via a version-prefixed `APIRouter` include), each producing its own `/api/v1/openapi.json` document, rather than one document with version-conditional paths.
- CI diffs the generated spec against the previous release's spec (a simple JSON diff step); any removed field/type-change/removed-endpoint on the current major version fails the build.

## 8. Examples
Every Pydantic model includes a `model_config = ConfigDict(json_schema_extra={"examples": [...]})` (Pydantic v2 idiom), which FastAPI surfaces directly as OpenAPI `examples` — kept consistent with the illustrative payloads in `11-api-contracts.md`.

## 9. Contract-Testing Usage
- The generated spec is the single artifact both the Angular Dashboard's `openapi-typescript`-generated client and the Flutter apps' generated Dart client consume — guaranteeing all three clients and the backend can never silently drift.

## Best Practices
- Every route has a `summary` and `description`; the generated spec is written to be genuinely readable by a new integrator, not just machine-parseable.
- FastAPI's automatic validation-error responses are always included in a route's documented `responses=`, not left as an undocumented implicit `422`.

## Risks
- FastAPI's default validation-error status is `422`, not the RFC 7807-style `400` used elsewhere in this design — **explicitly overridden** via a custom exception handler for `RequestValidationError` so the API surface is consistent (`400` for all shape-validation failures, matching `10-api-design-guidelines.md` §12), rather than leaking FastAPI's default behavior inconsistently into the contract.

## Alternatives Considered
- Hand-authored OpenAPI YAML with code generated from it (true "spec-first") — rejected; FastAPI's Pydantic-driven code-first generation is idiomatic for this stack and avoids a duplicate-maintenance burden between hand-written YAML and actual Pydantic models.

## Future Scalability
- The shared schema/response/parameter component structure (§2, §4, §5) is versioned alongside new major API versions, with only genuinely-changed schemas duplicated into a `v2`-specific module — minimizing spec maintenance overhead across a 10-year horizon.
