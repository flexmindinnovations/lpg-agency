# 25 — Lovable Prompts

## Purpose
Generates optimized Lovable prompts for major screens, each including business context, user goal, required components, interactions, accessibility, animations, responsive behavior, expected deliverables, design tokens, and modern SaaS styling direction.

## Scope and Approach
Given the platform's 61-screen inventory (`05-screen-inventory.md`), this document provides a reusable prompt template plus fully worked prompts for the highest-value screens (one per app, chosen for complexity/representativeness). Every other screen's prompt is generated by an implementer/AI agent following this exact template, populating it from that screen's entry in `05-screen-inventory.md` (purpose, roles, actions) and its corresponding template in `07-wireframe-specifications.md` (states, keyboard, accessibility) — the template's completeness is what makes this scale to all 61 screens without needing 61 hand-written documents.

## Prompt Template

BUSINESS CONTEXT: one to two sentences from docs/business/overview.md and the relevant docs/modules file — what real-world problem this screen solves.
USER GOAL: from 05-screen-inventory.md Purpose column plus 02-user-personas.md's relevant persona goal.
REQUIRED COMPONENTS: from 12-component-library.md — list every component this screen uses.
INTERACTIONS: primary and secondary actions from 05-screen-inventory.md, state transitions from docs/data/08-state-machines.md if applicable.
ACCESSIBILITY: from 07-wireframe-specifications.md's accessibility field for this screen's template, plus 17-accessibility.md general requirements.
ANIMATIONS: from 20-animation-guidelines.md, scoped to this screen's specific transitions.
RESPONSIVE BEHAVIOR: from 07-wireframe-specifications.md's responsive field plus 19-responsive-design.md.
EXPECTED DELIVERABLES: Angular standalone component or Flutter widget, matching the 23/24 design guidelines documents' conventions.
DESIGN TOKENS: reference 09-design-tokens.md — never hardcode; use semantic/component token names.
STYLING DIRECTION: Modern enterprise SaaS aesthetic benchmarked against Linear, Stripe Dashboard, Atlassian, GitHub, Vercel, Notion — calm, low-chrome, high information density where needed, never decorative for its own sake.

## Worked Prompt 1 — Order Queue (Dashboard, D-03)

BUSINESS CONTEXT: Agency staff need to see every incoming refill booking and move it toward fulfillment. This is the highest-traffic screen in the Dashboard — the entry point to the entire delivery pipeline.
USER GOAL: Dispatcher/Manager needs to scan pending orders, filter by status/branch/date, and select orders to build into a delivery route.
REQUIRED COMPONENTS: Data Grid (AG Grid Community; Enterprise only if grouping is enabled for this grid), Filter Bar, Page Header with primary Create Order button, Bulk Action Bar, Status Pill (per Order state), Column Chooser.
INTERACTIONS: Row click opens Order Detail. Multi-select rows enables an Add to Route bulk action. Filter Bar defaults to active statuses only (excludes Closed/Cancelled). Sort defaults to Requested Date ascending.
ACCESSIBILITY: Grid role semantics with sort-state on headers; arrow-key row navigation, Enter opens detail, Space toggles selection; bulk-selection count announced via a polite live region; filter inputs properly labeled.
ANIMATIONS: Skeleton rows on load (never a blank spinner); row fade-plus-height animation (150ms) on filter-driven insert/remove; no animation on initial data population.
RESPONSIVE BEHAVIOR: Full grid on desktop/tablet; converts to a stacked card-list (showing Order ID, Customer, Status, Date per card) below 768px, with filters accessible via a collapsed drawer.
EXPECTED DELIVERABLES: Angular standalone component composed of shared DataGrid, FilterBar, and BulkActionBar components from the shared UI library — container component owns state via an injected Orders facade service.
DESIGN TOKENS: dataGrid component tokens, status-color tokens for Status Pills, medium spacing for page margins.
STYLING DIRECTION: Modern enterprise SaaS aesthetic benchmarked against Linear, Stripe Dashboard, Atlassian, GitHub, Vercel, Notion — calm, low-chrome, high information density, never decorative for its own sake.

## Worked Prompt 2 — Route Planning Board (Dashboard, D-08)

BUSINESS CONTEXT: Every morning, a Dispatcher must group the day's confirmed orders into efficient delivery routes and assign a driver plus vehicle to each, checking that the vehicle's stock will cover the route's demand (BR-09).
USER GOAL: Build one or more routes quickly with live feedback on vehicle capacity, without needing to manually calculate stock sufficiency.
REQUIRED COMPONENTS: Three-panel layout (unassigned Orders list, Route builder drop-zone, Driver/Vehicle assignment panel), draggable Order Cards, Capacity Gauge, Driver/Vehicle Select dropdowns, Add to Route button (keyboard-accessible alternative to drag).
INTERACTIONS: Drag an order card into the Route panel, or select plus click Add to Route. Selecting a driver/vehicle live-updates the Capacity Gauge. Create Route commits the draft.
ACCESSIBILITY: Every drag interaction has a full keyboard equivalent (select via Space, move via a visible button/Command Palette action); capacity changes announced via a live region as orders are added/removed.
ANIMATIONS: Order card lift/shadow on drag start; capacity gauge fill animates smoothly (250ms) as orders are added/removed, never an instant jump.
RESPONSIVE BEHAVIOR: Desktop/tablet three-panel layout; mobile degrades to a simplified sequential flow (select orders, then driver/vehicle, then create) rather than the drag-based board.
EXPECTED DELIVERABLES: Angular standalone component using Angular CDK drag-drop for the drag interaction with a fully keyboard-operable fallback path, composed from shared Card, Select, and a new domain-specific CapacityGauge component.
DESIGN TOKENS: elevation level 2 for the dragging card, warning/danger status colors for the capacity gauge nearing/exceeding limit, medium motion duration.
STYLING DIRECTION: Modern enterprise SaaS aesthetic benchmarked against Linear, Stripe Dashboard, Atlassian, GitHub, Vercel, Notion — calm, low-chrome, high information density, never decorative for its own sake.

## Worked Prompt 3 — Book Refill (Customer App, C-06)

BUSINESS CONTEXT: Booking a refill is the platform's core consumer-facing transaction, replacing today's phone-call-during-business-hours process.
USER GOAL: A Customer wants to order a refill in under a minute, seeing their current cylinder balance for context and choosing how to pay.
REQUIRED COMPONENTS: Cylinder Balance Card (shows current filled/empty), Quantity Stepper, Address Selector (defaults to primary), Payment Method Selector, primary Submit button.
INTERACTIONS: Quantity stepper respects the customer's cylinder cap (BR-04) with inline messaging if exceeded; address defaults to primary but is changeable; submit shows inline loading, then navigates to Order Tracking on success.
ACCESSIBILITY: Large touch targets (48dp minimum) throughout given the broad age/comfort range of the Customer persona; every icon paired with a text label; form errors announced and associated with their field.
ANIMATIONS: Stepper value change has a subtle scale-pulse (100ms) for tactile feedback; submit button shows an inline spinner without layout shift; success transitions to Order Tracking with a gentle cross-fade (250ms).
RESPONSIVE BEHAVIOR: Single-column, portrait-primary mobile layout; landscape not specially optimized for this action screen.
EXPECTED DELIVERABLES: Flutter widget using Riverpod Notifiers for state, composed from shared CylinderBalanceCard, NumericStepper, AddressSelector, and PaymentMethodSelector widgets in the shared design-system package.
DESIGN TOKENS: Customer App's slightly larger body-text token (17px), large spacing between form sections, primary action color for the submit button.
STYLING DIRECTION: Warmer, friendlier tone than the Dashboard while still calm and trustworthy — a modern consumer fintech/utility-app feel, not playful or gamified.

## Worked Prompt 4 — Delivery Confirmation (Driver App, DR-05)

BUSINESS CONTEXT: This screen captures the required Proof of Delivery (BR-08, BR-23: OTP plus signature plus photo plus GPS) that protects both the customer and the agency from disputes, and must work with zero connectivity (D-24).
USER GOAL: A Driver wants to confirm a delivery in under 30 seconds, one-handed, in bright sunlight, with zero risk of losing already-captured data if a step fails.
REQUIRED COMPONENTS: Numeric Steppers (quantity confirmation), OTP Input (6-digit, large), Signature Pad, Camera capture button, sequential progress indicator.
INTERACTIONS: Sequential flow — quantity confirm, OTP entry, signature, photo, final confirm (enabled only once all four captured). A Report an Issue escape hatch is available at every step, routing to Failed Delivery.
ACCESSIBILITY: Very large touch targets (48dp+) given outdoor/gloved/one-handed use; high contrast mode essential; every icon paired with text (never icon-only) given the Driver persona's variable tech comfort.
ANIMATIONS: None beyond instant, zero-lag stroke rendering on the signature canvas; a brief full-screen success animation on final confirm before auto-advancing to the next stop.
RESPONSIVE BEHAVIOR: Mobile-only, portrait-locked; no tablet/landscape variant for this screen.
EXPECTED DELIVERABLES: Flutter widget with all captured data written to local Drift storage immediately (before any network call), queued for background sync via the offline sync engine — the UI must never appear to wait on network for any step in this flow.
DESIGN TOKENS: Driver App's high-contrast token set, larger touch-target component tokens, danger status color for the Report an Issue action.
STYLING DIRECTION: Maximum clarity and legibility over visual polish — this is a working tool used outdoors under time pressure; every element must be instantly recognizable at a glance.

## Best Practices
- Every Lovable prompt cross-references the exact source documents (screen inventory entry, wireframe template, component specs, tokens) it was derived from, so a prompt can be regenerated or audited against the design system if the underlying spec changes.
- Prompts never invent new business logic, copy, or validation rules not already present in the approved SRS/API/domain-model documentation — a prompt's job is to describe how to build an already-approved screen, never to design new behavior.

## Risks
- A prompt generated by strictly following the template but skipping a genuine cross-reference to the relevant wireframe/component spec risks under-specifying accessibility or state handling — mitigated by requiring the template's Required Components and Accessibility fields to cite specific document sections, not generic restatements.

## Alternatives Considered
- Hand-writing all 61 individual prompts — rejected as an unsustainable, drift-prone document given the size of the screen inventory; the template-plus-worked-examples approach scales without losing specification completeness, mirroring the same pattern applied in `07-wireframe-specifications.md` and `13-component-specifications.md`.

## Future Scalability
- As new Phase 2 screens are added to `05-screen-inventory.md`, their Lovable prompts follow this exact template without requiring a new prompting methodology.
