## Nx

Purpose

Workspace and module-boundary enforcement for the Angular workspace at `frontend/`.

Responsibilities

- Affected-project detection to keep monorepo CI times bounded

Nx is the frontend counterpart of `import-linter` on the backend: the same principle, enforced the same way (ADR-018).

---

## State Management — Signals First

Applied as an ordered rule set (ADR-019). The first rule that fits is the answer.

1. **Angular Signals** for local and component state — the default.
2. **NgRx SignalStore** for complex feature-level or shared application state where centralized reactive state is genuinely justified (server-side filter/sort/pagination, state shared across sibling routes, state surviving navigation).
3. **No classic NgRx** Store/Actions/Reducers unless a documented need is recorded as an ADR.
4. **RxJS** for HTTP, WebSocket streams, debounced input, and async orchestration — converted to Signals at the boundary via `toSignal()`.
5. **Never** introduce a state library for simple component state.

## AG Grid Enterprise

Purpose

Enterprise data grids: large datasets, filtering, grouping, export, virtual scrolling, column management, saved views.

**Three binding constraints (ADR-020):**

1. AG Grid is **encapsulated behind application-level grid components** in `libs/shared/ui`.
2. Feature libraries **must not** import AG Grid types or call AG Grid APIs directly — they configure the wrapper through an application-defined contract. A wrapper that leaks AG Grid types is not an abstraction.
3. **AG Grid Enterprise is a commercial, paid-licence product.** The licence key is supplied as build-time environment configuration from the secret store and is never committed.

The architecture must remain replaceable if licensing or product requirements change. Licence procurement is currently **unconfirmed** — it blocks the Angular Foundation phase.

**PrimeNG is not adopted.** With AG Grid for grids and Angular Material + CDK for interaction primitives, a third component library would only fragment the design-token implementation.

## Redis

Purpose

In-memory data store.

Used for

- Caching (tenant configuration, permission sets, KPI aggregates)
- Sessions
- Rate Limiting
- Background job queue
- **Real-time Pub/Sub backplane** (ADR-015)
- Temporary Data

Because Redis serves five distinct roles, it is a **critical dependency** and monitored as one. Its failure degrades live updates and background processing; it must not break core transactional operations.

---

## Background Jobs

A **separate worker process** sharing the backend codebase, with Redis as the queue substrate. Jobs are application-layer use cases, never logic that exists only inside a scheduler, and every job runs inside a tenant context.

**The specific library is deferred** to the Backend Foundation phase — ARQ, Dramatiq, and Celery are the candidates (ADR-023).

---

## Architecture Enforcement

- **`import-linter`** — Clean Architecture dependency rule and bounded-context isolation, merge-blocking in CI
- **`mypy --strict`** — type coverage at layer boundaries
- **`structlog`** — structured JSON logging with tenant/correlation context and central redaction

These are not optional tooling preferences. Python has no compiler-enforced layer contracts, so these checks are what make the architecture real (ADR-024).

# Database

## PostgreSQL

Purpose

Primary relational database. **Hosted on Supabase** (ADR-027) as a managed Postgres host and nothing more — Supabase Auth, Storage, Realtime and Edge Functions are **not** adopted. Local development uses Docker Compose PostgreSQL 17.

Two non-negotiable rules follow:

1. **Alembic owns the schema.** Never use Supabase's migration tooling, SQL editor, or the MCP `apply_migration` tool to change schema. Two migration systems on one database produce a schema neither can describe.
2. **Never connect the application as `service_role`.** That key bypasses Row-Level Security by design, removing the tenant-isolation backstop. Use a dedicated `NOSUPERUSER`, `NOBYPASSRLS` role.

Responsibilities

- Business Data
- Transactions
- Reporting
- Audit Data

Reasons for selection

- Reliability
- Performance
- JSONB Support
- Full-text Search
- Excellent Python ecosystem

# Technology Selection Principles

When introducing new technologies:

- Prefer mature solutions.
- Avoid unnecessary dependencies.
- Ensure long-term community support.
- Maintain consistency with the existing stack.
- Evaluate security and licensing.
- Consider operational complexity.

Technology should be adopted only when it clearly improves the platform.

---

# AI Development Guidelines

Before using a library or framework:

1. Check whether an approved technology already solves the problem.
2. Prefer existing project dependencies.
3. Avoid introducing duplicate libraries.
4. Follow project engineering standards.
5. Document any new dependency.

Never replace core technologies without architectural approval.
