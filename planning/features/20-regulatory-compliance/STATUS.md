## Exception: Weighment — 🟢 DONE

A second item, this time `PLAN.md`'s own explicit Tier-0 priority ("cheap effort, high consequence" — mirrored in `docs/research/feature-gap-analysis.md` §5), was built as its own narrower slice: MDG 2022 cl. 1.2 (goods-receipt scale + 10% sample) and cl. 1.4(c)(d) (100% load-out check). Regulatory numbers were researched, not invented: ≤10g scale least count and the 10%/100% sample sizes trace to MDG 2022 cl. 1.2/1.4, already cited in `docs/research/feature-gap-analysis.md` R1; the 150g domestic-cylinder (14.2kg) tolerance is a **new finding**, not previously in this repo's own research (medium confidence — multiple independent sources agree it derives from the Legal Metrology (Packaged Commodities) Rules, 2011, but no exact rule-number citation was pinned down), so it is seeded as a tenant-configurable `weighment_tolerance_grams` default, not a hard constant. MDG editions are per-OMC, not one national standard — this repo's citations are HPCL's 2022 edition; a tenant on a different OMC/edition (e.g. IOCL's 2024 edition) should confirm its own thresholds before relying on the seeded defaults. Gates re-run and green, not assumed:

- **Scale registry + goods-receipt sample capture** (`b3a6fc1`, `fc03924`): standalone `Scale` aggregate (`compliance.scale`, RLS, ≤10g least-count invariant per MDG cl. 1.2(ii)(iii)) and `WeighmentRecord` (`compliance.weighment_record`, append-only, batch-level not per-serial — ADR-039), `weighment:manage`/`weighment:record` permissions, `weighment_tolerance_grams` (default 150) / `weighment_scale_least_count_max_grams` (default 10) `TenantConfiguration` keys, non-blocking `POST /goods-receipt-notes/{id}/weighment`.
- **100% load-out gate** (`e6d579e`): `LoadVehicleForRouteUseCase` blocks `planned → loaded` (409 `WEIGHMENT_CHECK_REQUIRED`) when a manifest cylinder type has no passing `load_out_full_check` record — but only for a tenant that has opted in via the `weighment_gate_enabled` config key (default off, ADR-040). This was not the original design: wiring the gate in unconditionally was found, via the full backend test suite (not just this feature's own tests), to break 3 pre-existing integration tests by turning every tenant's ordinary dispatch into an immediate 409 — no tenant has ever recorded a weighment, since the feature is new. The opt-in redesign was raised to and decided by the user directly rather than assumed; all 3 previously-broken tests pass again with the default-off flag, and 5 new unit tests cover the full gate matrix (off, on+missing, on+failing, on+passing, no-repos-wired).
- **Dashboard** (`3dae8a5`): new Scales registry page (`/scales`, Logistics nav) — grid, register/detail drawers, expiry filter, recalibrate, activate/deactivate; a GRN weighment mini-form (10% sample, non-blocking, surfaced as an optional second step after "Receive Goods"); a route load-out weighment mini-form ("Log Load-Out Weighment" in the Route Detail drawer, independent of Load Vehicle, listing recorded checks per cylinder type with a pass/fail tag). Live-verified in-browser against the real dev backend: scale registration (≤10g clamp enforced client-side by PrimeNG's `[max]`, required-certificate validation blocking submit, expiry filter narrowing correctly, recalibrate/status-toggle round-tripping), a GRN → weighment-sample `POST` (201), and a route load-out weighment `POST` (201, Pass tag rendered from a real 0-underweight result).
- **Gates:** targeted + full-repo `ruff check`/`mypy` clean on every touched backend file; backend unit + integration suites for `Scale`, `WeighmentRecord`, and the load-out gate all pass, plus a full ~1203-test backend regression run after the opt-in redesign (the 3 previously-broken tests confirmed green again); frontend `lint`+`test` clean for every touched/new library (`compliance-feature-scales`, `shared-data-access`, `inventory-feature-inventory`, `feature-dispatch`, `dashboard`) and a full repo-wide `lint`+`test` run, clean aside from two pre-existing, unrelated spec failures (`feature-complaints`, `feature-employees` — missing DI providers in their `TestBed` setup, last touched in commits predating this work) flagged separately as a background task, not fixed inline since out of scope.
