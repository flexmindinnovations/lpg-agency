## Audit Findings (2026-08-12) — historical, now resolved

An independent re-verification on 2026-08-12 found the phase's prior "COMPLETE" claim false:

1. Zero backend tests for `Route`.
2. `import-linter` contract broken (API layer importing SQLAlchemy directly).
3. `feature-dispatch`'s `project.json` had empty `tags: []`, failing `dashboard:lint`.
4. Frontend was a route list + create-only shell — no dispatch board, no order-to-route assignment, no POD/failed-delivery handling.
5. `VehicleLoadEvent`/`VehicleShiftReconciliation`, named in the original plan's scope, were never implemented.
6. A real correctness bug: `FeatureDispatch.onSubmitPlan()` hardcoded `branchId = this.branches()[0].id`.
7. One `ruff` import-order error.

All seven are resolved — see below. Two further real bugs were found and fixed *while writing tests* against the pre-existing `Route`/`RouteStop` scaffold (not part of the original audit, but the same class of finding):

8. `SqlAlchemyRouteRepository.save()` never called `session.flush()`, so a route created earlier in the same request was invisible to a subsequent `get_by_id()` (`Session.get()` bypasses autoflush) — surfaced as spurious 404s on `AssignOrderUseCase`'s find-or-create path.
9. Nothing ever transitioned a route from `in_progress` to `completed` once every stop was resolved, making `POST /routes/{id}/reconcile` structurally unreachable. Fixed with `Route._auto_complete_if_all_stops_terminal()`, called from the POD/failure/cancel-stop paths — and this exact behavior was independently confirmed live in the browser (see Verification).

## Scope resolution

`Route`/`RouteStop` became the real dispatcher-facing grouping construct, replacing Order Management's interim `driver_id`/`vehicle_id` columns exactly as that migration's own docstring instructed. `VehicleLoadEvent`/`VehicleShiftReconciliation` were deliberately descoped — both would have duplicated Inventory Management's existing load-transfer and reconciliation infrastructure. Full rationale in `PLAN.md` and `docs/data/01-domain-model.md` §4.4's divergence note (same class of documented divergence as Phase 7's Branch/Warehouse/TenantConfiguration note).

## Post-completion UI fixes (2026-08-13, same day, user-reported)

After close-out, live use surfaced four real UI defects in the shipped Order Management/Dispatch frontend, all fixed and independently verified (build + lint + live browser), not just code-reviewed:

1. **Order Detail header overlap** — the order ID (full UUID) and status badge were crammed into one `<h1>` with no wrap handling, visually colliding at normal and narrow widths. Fixed: split into a heading + a wrapping `.order-title-row`, ID truncated to its first UUID segment (matching this codebase's existing truncation convention elsewhere) with a proper `pTooltip` showing the full ID on hover.
2. **"Amount Collected" currency field** — used PrimeNG's masked `mode="currency"` input, which both looked like it might be missing its ₹ symbol and had a real data-entry bug (typing over the masked value inserted digits into the mask instead of replacing it — confirmed live: typing "950" over "₹0.00" produced "₹9,500.01"). Fixed: switched to a plain numeric input with a static `p-inputgroup-addon` ₹ prefix; confirmed live that typing "950" now yields exactly `950`.
3. **Checkbox-driven row selection replaced with real links**: four grids (Orders, Customers, Drivers, Vehicles) used AG Grid's checkbox row-selection as an implicit "act on this row" trigger. Added a new `onLinkClick` capability to the shared `DataGridComponent` (`libs/shared/ui`) — a real, keyboard-accessible `<button>` styled as a link, rendered via a new `DataGridLinkCell` AG Grid cell renderer, which also suppresses the checkbox column automatically when present. Wired into all four grids, each keeping its existing action (Orders → navigate to detail; Customers → open detail panel; Drivers/Vehicles → open status-update modal). Orders' grid also had its "Order ID" column moved to the first position per user request.
4. **A real, app-wide, previously-undiscovered bug — now closed**: PrimeNG v22 (the version this project has installed) removed the `icon`/`label` string inputs from the `[pButton]` **directive** (confirmed by reading the compiled directive's declared inputs in `node_modules/primeng/fesm2022/primeng-button.mjs` — no `icon` or `label` among them, as of PrimeNG v21+). Every `<button pButton icon="pi pi-x">Text</button>` across the **entire application** — not just this phase's — was therefore silently rendering with no icon since whichever phase first wrote it. `<p-button>` (the separate, unrelated *component*, not directive) is unaffected and was never touched. The fix: project the icon as real content (`<i pButtonIcon class="pi pi-x">`) and — the non-obvious part, found by hitting it live — also wrap the button's text in `<span pButtonLabel>...</span>`, otherwise `ButtonDirective`'s `isIconOnly` check (which looks for a `pButtonLabel`-typed content child, not just any text node) forces icon-only sizing and clips the label. Fixed and live-verified in `order-detail`, `feature-dispatch`, and `order-queue` directly; a full app-wide sweep then fixed the remaining **36 button instances across 15 files** spanning `inventory-feature-inventory` (6), `delivery-feature-drivers`/`delivery-feature-vehicles` (1 each), `customer-feature-customers` (4), `admin-feature-audit-log` (2, including the one genuinely icon-only case — a Refresh button correctly left without a `pButtonLabel`, using `aria-label`/`pTooltip` instead), `admin-feature-tenant-settings` (15, across its five sub-pages), `admin-feature-users` (4), and `apps/dashboard/home` (2). Independently re-verified (not trusted from the sweep's own report): a fresh, uncached `nx build dashboard` — zero TypeScript errors; fresh lint on all 9 touched projects — 8/9 clean, the 9th (`customer-feature-customers`) failing only on a pre-existing `@nx/enforce-module-boundaries` violation from an unrelated, concurrently-in-progress session building `libs/ledger/feature-ledger` (a new, untracked library that appeared mid-session — not part of this fix, not touched, confirmed by timestamp and by the fact the violating import/usage predates this fix's edits to that file); and direct source-code inspection of the generated markup in 4 of the 15 files confirming the exact correct icon+label pairing throughout, plus a `pButtonIcon`-vs-`pButtonLabel` count sanity check (55 vs 54, the one-count gap being exactly the single genuine icon-only button) across the whole frontend showing zero remaining unfixed instances.
